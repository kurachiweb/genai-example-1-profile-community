# ADR: プロフィール検索（BR-DISC-004）の実装方式 — FTS5 を採用せず正規化列＋LIKE を用いる

- **ステータス**: 承認済み（Accepted）
- **日付**: 2026-06-03
- **対象**: `BR-DISC-004`（プロフィール検索） / `docs/GUIDES/db/01-data-model.md` §6

## 文脈

閲覧者は実効公開のプロフィールを **表示名（氏名）と職業** で検索できる（[04-profile-discovery.md](../service/features/04-profile-discovery.md) `BR-DISC-004`）。
当初、部分一致を SQLite の `LIKE` で行うか **FTS5** で行うかが「オープン事項」として未決のまま残っていた（旧 `01-data-model.md` の注記）。

決定にあたって踏まえた要件・前提は次の通り。

### 検索要件（`BR-DISC-004`）

- 対象は **表示名（氏名）と職業** の 2 フィールドのみ。各 ≤50 書記素の短い文字列。
- **部分一致・大文字小文字非依存**。日本語は表記揺れに配慮し、可能な範囲で **NFC 正規化**（`BR-COMMON-009`）して比較する。
- 既定ソートは **関連度**（または新着を選択可）。
- **カーソルページング**（公開 API と整合、`BR-DISC-003`）、**短 TTL キャッシュ**（`BR-DISC-006`）、**実効公開フィルタ**（`BR-DISC-001`）が前提。
- 未認証の検索は IP 単位レート制限（60 req/分、`BR-COMMON-010`）の対象。

### 技術前提

- デプロイ先は **Cloudflare D1**（マネージドな SQLite 互換）。**カスタム拡張・カスタムトークナイザを読み込めない**。
- ORM は **MikroORM**。
- 規模は個人開発アプリ。低コスト・低運用負荷を重視。

## 検討した選択肢

### 選択肢 A: 正規化 `search_name` 列＋`LIKE`＋簡易関連度（採用）

- **Pros**: 中間一致（部分一致）が `LIKE '%語%'` で自然に満たせる。日本語のトークナイズ不要。MikroORM で素直に扱える。カーソルページングを公開 API と揃えやすい。実装・運用が単純。
- **Cons**: 中間一致は B-tree インデックス非適用で全表スキャンに依存（現規模で許容）。BM25 相当の精緻な関連度は持たない（簡易ヒューリスティックで代替）。

### 選択肢 B: FTS5 + `trigram` トークナイザ

- **Pros**: BM25 による関連度ランキングが標準で得られる。転置インデックスで件数増に強い。`trigram` なら CJK の部分一致にも対応。
- **Cons**: `trigram` は **3 文字以上が前提**で、AC-DISC-005「里中」のような **2 文字検索を取りこぼす**。標準トークナイザ（`unicode61` 等）は CJK を語分割せず、MeCab/ICU 等の形態素トークナイザは **マネージド D1 で読み込めない**。仮想テーブルは MikroORM の一級市民でなく、`profiles` との同期（トリガ/アプリ層）が必要で `BR-DISC-006`（鮮度・整合）の実装が複雑化。BM25 スコア順は安定したカーソルキーを作りにくい。シャドウテーブルで D1 の行読み取り・ストレージが増える。

### 選択肢 C: ハイブリッド（検索層を抽象化し将来 BM25 へ差替え）

- **Pros**: v1 は A で実装しつつ、将来 FTS5/外部検索へ差し替えられる。
- **Cons**: v1 時点では抽象化が過剰（YAGNI）。

## 決定

**選択肢 A を採用する。v1 では FTS5 を採用しない。**

- 検索用の導出列 **`search_name`** を `profiles` に持たせる。`first/middle/last` ＋表示順から表示名を組み立て、**NFC 正規化・ケースフォールド**した値を保存する（アプリ層で保守）。
- **職業** は単一フィールドのため、NFC 正規化済み（`BR-COMMON-009`）の値にクエリ時ケースフォールドして `LIKE` 比較する。
- 部分一致は `LIKE`、既定ソートの **関連度は簡易ヒューリスティック**（完全一致 ＞ 前方一致 ＞ 部分一致、氏名一致 ＞ 職業一致）で実装する。
- 結果は **短 TTL キャッシュ**（`BR-DISC-006`、KV `cache:profiles:<query-hash>`）で鮮度と性能を両立する。
- 前方一致の高速化のため `idx_profiles_search_name` を張る（中間一致はインデックス非適用）。

## 結果・影響

### 正の影響

- マネージド D1 の制約と日本語の部分一致要件に正面から適合する。
- 実装・運用が単純で、仮想テーブルの同期コストを負わない。
- カーソルページングを公開 API のカーソル方式と揃えやすい。

### 負の影響・トレードオフ

- 中間一致は全表スキャン依存（現規模では許容。レコード増時に劣化しうる）。
- BM25 相当の関連度は持たない（簡易ヒューリスティックで代替）。
- 緩和策として **検索処理を分離（検索層として抽象化）して実装**し、将来 FTS5/外部検索へ差し替えられる余地を残す。

## 将来の見直しトリガ

次のいずれかが顕在化した場合、FTS5（`trigram`）または外部検索（例: 専用検索サービス）を再評価する。

- プロフィール件数の増加で `LIKE` 中間一致の応答が劣化する。
- 検索対象の拡張（自己紹介・タグ等、[04-profile-discovery.md](../service/features/04-profile-discovery.md) §5）。
- 日本語形態素解析やより高度な関連度ランキングが必要になる。
