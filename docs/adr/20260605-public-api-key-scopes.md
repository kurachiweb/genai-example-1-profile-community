# ADR: 公開API キーに read / full の 2 スコープを導入

- **ステータス**: 承認済み（Accepted）
- **日付**: 2026-06-05
- **対象**: 公開API（`apps/public-api`）の **API キー認可スコープ** / [05-public-api.md](../service/features/05-public-api.md) §2・§3・§5・§6、[db/01-data-model.md](../GUIDES/db/01-data-model.md) §5.4、[glossary.md](../service/glossary.md) §6、[07-admin-console.md](../service/features/07-admin-console.md) `BR-ADMIN-007`

## 文脈

公開API のキーは従来「キー＝本人権限（本人フル CRUD）」として設計され、スコープ細分化（Read 専用キー等）は [05-public-api.md](../service/features/05-public-api.md) §8 に**オープン事項（将来課題）**として残っていた。本 ADR でこの判断を確定する。

判断を分ける要因は **キーの利用形態**であった。前提は次の通り。

### 公開API の権限面と既存の緩和策

- 書き込み面は**本人の自プロフィールのみ**（`PUT`/`PATCH`/`DELETE /me/profile`）。破壊的・不可逆操作（退会・メール/パスワード変更・WebAuthn パスキー操作・通報・管理操作）は既にAPIから除外済み（`BR-API-010`、[01-user-account.md](../service/features/01-user-account.md) `BR-ACCT-009`/`BR-ACCT-010`）。
- フル権限キー漏えい時の最悪ケースは「本人の自プロフィールの上書き・消去（内容消去＋非公開化）」のみ。アカウントは存続し画面から復旧可能で、**単一リソース・回復可能**。
- 既存の緩和策: いつでも失効可（`BR-API-002`）、キー単位レート制限 60 req/分（`BR-API-008`）、発行・失効の監査ログ（`BR-COMMON-013`）、ハッシュ保存・一度限り表示（`BR-API-001`）。

### キーの利用形態（決め手）

- `BR-API-008` の根拠は「自作サイト埋め込み等の通常利用に十分」であり、**キーがクライアント（ブラウザ）に露出する**使い方を想定している。露出前提だとフル権限キーの書き込み権が常時さらされ、実害確率が上がる。
- 想定利用形態は**クライアント埋め込み**であると確定した。したがって、漏えいしても被害が読み取りに限定される **Read 専用キーを提供する価値が大きい**。

### 実装前提

- `apps/` 配下は未実装で、`api_keys` テーブルにスコープ列はない（[db/01-data-model.md](../GUIDES/db/01-data-model.md) §5.4）。**実装着手前の今なら移行コストが極小**で、ローンチ後の追加より大幅に安い。
- 管理者はキーのメタ情報閲覧と失効のみ可能（`BR-ADMIN-007`/`BR-ADMIN-008`）。スコープ操作機能は持たせない方針。

## 検討した選択肢

### 選択肢 A: 現状維持（キー＝本人フル権限のみ）（不採用）

- **Pros**: 最小コスト・最小複雑性。スキーマ・UI・ガード・ドキュメントの追加がゼロ。書き込み面が小さく回復可能なため、サーバーサイド利用に限れば許容できる。KISS/YAGNI に素直。
- **Cons**: クライアント埋め込み前提では、漏えいしたフル権限キーで本人プロフィールの上書き・消去が可能になる。最小権限の原則に反し、想定利用形態（埋め込み）とリスクが噛み合わない。

### 選択肢 B: read / full の 2 スコープを v1 で導入（採用）

- **Pros**: 最小権限の原則を満たす。`read` キーは埋め込んでも漏えい時に読み取りのみ（他者分は実効公開 `BR-COMMON-007` に限定）で被害が限定される。実装前の今なら移行コストが極小。2 スコープに限定するため複雑性も限定的。
- **Cons**: スキーマ列・発行 UI のスコープ選択・認可ガードのスコープ判定・関連ドキュメントの水平展開（features 05/06/07・glossary・data-model・overview）が必要。

### 選択肢 C: スキーマ前方互換のみ（`scope` 列を `full` 既定で先行定義し機能は将来）（不採用）

- **Pros**: 将来のマイグレーションを回避しつつ v1 の挙動は不変。決定を遅延できる。
- **Cons**: 想定利用形態がクライアント埋め込みである以上、`read` キーを提供しないと v1 時点のリスクが解消されない。オープン事項が条件付きで残り続け、今回の目的（判断確定）に反する。

## 決定

**選択肢 B を採用する。公開API キーに `read` / `full` の 2 スコープを v1 で導入する。**

- 各キーは発行時にスコープを 1 つ選択し、**発行後は変更不可**（権限の暗黙昇格を防ぐ。昇格は失効＋再発行。キー値ハッシュ不変の方針と整合）。
- `read`: Read 系のみ（`GET /me/profile`・`GET /profiles/{handle}`・`GET /profiles`）。`full`: 上記に加え本人プロフィールの書き込み（=従来の本人フル CRUD）。
- `read` キーで書き込みエンドポイントを呼ぶと `403 FORBIDDEN`（スコープ外操作、`BR-API-011`）。
- **クライアント埋め込みは `read`、`full` はサーバーサイド限定でクライアントに埋め込まない**運用ガイダンスを明示する（`BR-API-010b`）。
- レート制限はスコープ非依存でキー単位 60 req/分のまま（`BR-API-008` 変更なし、スコープ別しきい値なし）。
- 凍結・退会時は**全スコープのキーを一律無効化**（`BR-SAFE-006`/`BR-ACCT-009`、`read` も例外なし）。有効キー上限はスコープ合算で 5 個（`BR-API-002` 変更なし）。
- `api_keys` に `scope`（`TEXT(enum)` NN CHECK `read`/`full`）を追加。スコープ選択は監査ログのキー発行イベントに併記する。
- 実コード（認可ガード・MikroORM エンティティ・発行 UI）は `apps/public-api`・`apps/client` 実装時に整備する。本 ADR は**実装に先行する設計記録**であり、`BR-API-001b`・`AC-API-001b`・`AC-API-011b` が実装時のテスト基礎となる。

## 結果・影響

### 正の影響

- クライアント埋め込み向けに漏えい耐性のある `read` キーを提供でき、最小権限の原則を満たす。
- 書き込みは `full` スコープ・サーバーサイド限定に整理され、フル権限キーの攻撃面が縮小する。
- §8 のオープン事項が解消され、仕様が `read`/`full` で一貫する。

### 負の影響・トレードオフ

- スキーマ列・発行 UI・認可ガード・ドキュメントに追加・変更が生じる（2 スコープに限定して局所化）。
- 利用者はスコープ選択を理解する必要がある（発行画面とドキュメントでの明示で緩和）。

## 将来の見直しトリガ

- リソース別・項目別など**より細粒度のスコープ**が必要になった場合（[05-public-api.md](../service/features/05-public-api.md) §8 の残課題）。
- 書き込み専用や時間制限付きキーなど、2 スコープで表現できない要件が現れた場合。
